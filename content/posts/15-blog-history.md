# 1. 싫어하는 플랫폼: AWS Amplify

AWS의 많은 서비스들을 좋아하고, 흥미가 있어서 내부 동작까지 찾아보며 공부해 본 경험이 있습니다. 하지만, AWS Amplify에 대해서는 아쉬움을 느꼈습니다.

AWS Amplify는 풀스택 애플리케이션 개발을 지원하는 플랫폼입니다. 최근 진행했던 챗봇 웹 서비스 프로젝트를 Amplify로 배포했었는데, 해당 환경에서는 streaming respons를 지원하지 않았습니다. 그 결과 챗봇의 응답은 전체 렌더링이 완료될 때까지 화면에 아무것도 표시되지 않았습니다.

이러한 챗봇 웹사이트나 LLM 기반 서비스에서는 스트리밍 방식의 응답이 필수적입니다. HTML을 스트리밍 하면서 fallback을 먼저 보여줘야 사용자가 기다리는 동안에도 내용을 확인할 수 있기 때문입니다. 하지만 해당 환경에서는 답변이 모두 생성될 때까지 기다려야 했고, 이는 사용자 경험이 저하되는 사례라고 느꼈습니다.

결국 AWS Elastic Beanstalk를 사용하도록 재배포했습니다. 또한 저와 같은 사례가 있는지 찾아보니, 아래 이슈에서 동일한 문제를 겪고 있는 사례가 많다는 것을 확인할 수 있었습니다.

(이슈 링크: https://github.com/aws-amplify/amplify-hosting/issues/3843)

다양한 비즈니스 모델이 필요한 것은 이해하지만, 2년이 넘는 시간 동안 문제를 인지하고도 개선이 이루어지지 않은 점에서 Amplify에 아쉬움을 느끼게 되었습니다.

# 2. 싫어하는 플랫폼: Vercel

저는 기술 블로그를 운영 중에 있습니다. 개인의 도메인으로 배포된 사이트가 있었으면 좋겠다고 생각해서 시작한 블로그였습니다.

Next.js로 만들어진 이 블로그는 처음에 Vercel로 배포되었습니다. 약 1년 정도 문제없이 사용했지만, 어느 날 블로그가 Paused 상태가 되었습니다. 확인해 보니 Fast Origin Transfer를 포함해서 4개의 리소스 사용량 초과가 있었습니다.

우선 20달러 결제를 하고 로그를 살펴봤습니다. Bot들의 요청이 무수히 발생했습니다. robot.txt를 추가하고 function invocations를 제어해 봤지만 큰 효과가 없었습니다. 오후 4시 기준 사용 요금이 1달러였는데, 오후 7시경 사용 요금이 2.5달러가 되었습니다.

문제를 해결하기 위해 AWS의 S3, CloudFront를 사용한 배포로 전환하기로 했습니다. 하지만 AWS로 전환 후, 2일 후에 Free 플랜 Request 50% 사용 메일을 받았습니다. AWS에서 확인을 해보니, 시간당 약 7595개의 요청이 찍혔습니다. 이 요청은 전부 미국이었습니다. 이에 지리적 제한을 추가했는데, 불필요한 요청들이 사라지게 되었습니다.

AWS CloudFront에서 클릭 한 번으로 가능한 기능임에도 불구하고 이러한 경험을 하게 되었다는 점과, 20달러 선결제 없이는 서비스 사용을 하지 못했다는 점에서 Vercel에 아쉬움을 느꼈습니다.

근데 이게 Trae AI로 가닥을 잡은 후에 개선해서 그런지, 예전 블로그랑 꽤 비슷한 것 같다. 그냥 UI만 조금 바꾼 느낌? 이지만.. UI/UX 하나하나 꽤 노력을 많이 들였다.

Trae로 만든 게 아까워서 그랬던 것 같다. 오히려 바로 Cursor AI로, "만들어줘" 했으면 쉬웠을거같은데, 가독성을 늘리려고 글자 크기나 화면 크기를 조정하는 등 여간 쉬운 일이 아니었다.

그리고 요새 AI로 사이트를 만들어달라고 하면, 구체적인 요구사항이 없을 때는 비슷한 형태의 UI/UX를 AI가 만들어준다. 이걸 AI 플롭 현상이라고 하는데, 이게 싫었다. 그래서 AI가 좋아하는 **그림자** 라던지, **hover 했을 때 살짝 들리는 기능** 같은 것들을 지우려고 했다.

아무튼 이렇게, 정상적으로 블로그를 운영하고있었는데, 어느날 블로그가 Paused 상태가 됐다.

# 블로그 정지

![](/blog-images/15/6.png)

저 때가 Vercel을 사용해서 블로그 배포한지 한 1년 정도 된 것 같은데, 저런 걸 처음 봤다.

Pause 상태가 됐을 때 사이트 접속도 안되고 로그 확인도 안됐었다.  
사이트가 운영중이어야 로그를 찍어볼텐데 해서 플랜 업그레이드를 하려고 했다.

Vercel은 20달러 선결제 방식이었다. 선결제 후, 사용량에 따라서 지불하는 방식이었다. 사용하지 않은 양은 환불이 가능했다.

로그를 찍어둔 사진은 없는데, 아래는 오후 4시 49분의 사진이다.
![](/blog-images/15/7.png)

Vercel의 observability 에서 로그를 봤는데, bot들의 무수한 요청들이 찍혀있었다. 거의 1~2초에 한번씩 왔었다.

아래 두 가지 방법을 시도해봤는데,
1. robot.txt를 추가해서 bot 요청을 막는 방법
2. Vercel 의 Function Invocations를 사용해서 봇의 요청을 제한하는 방법

크게 효과가 없는 것 같았다. 계속 봇들의 요청이 찍혔다.

이후 3시간정도 이후의 사진인데,
![](/blog-images/15/8.png)

가격이 **1.5불**이 늘었다. 이대로는 안될 것 같아서 정적 블로그로 바꿨다. 원래 nextjs 기반 동적 블로그였다.

<br>

![](/blog-images/15/9.png)
1시간 반 정도 후에 다시 확인해보니, 가격이 **0.2불**이 늘었다.  
많이 늘지는 않았지만 그래도 상승폭이 큰 것 같았다.

여기에 cloudflare를 붙일까 하다가.. Vercel에서 돈 더 빠져나가는 게 싫어서  
AWS의 S3 + CF 기반의 정적 블로그로 마이그레이션하기로 했다.

마이그레이션하고, Route53을 통해 구입한 도메인과 연결해줬다.

5일 정도 후에, CloudFront에서 메일이 왔다.
![](/blog-images/15/10.png)


CloudFront에서 로그를 살펴봤는데, 시간당 7500개의 요청이 찍히고 있더라.

게다가 이거 국가를 보니까, 전부 미국이었다.

![](/blog-images/15/11.png)

날짜별로 보니까, 3일정도의 시간동안 580000건의 요청이 찍히더라.  
프랑스도 있었는데, 거의 미국이었다.

![](/blog-images/15/12.png)

그래서 바로 CF의 지리적 제한을 걸어줬다. 예전처럼 콘솔로 하는게 아니라 rule manage에 들어가서 해야됐었다.

![](/blog-images/15/13.png)

설정해줬더니 사이트가 쾌적해졌다. CF 메일도 안왔다.

# 그래서 에세이에 적었다

그래서 Vercel 이라고 적었다.  
지리적 제한 저거 하나 추가하면 되는건데, vercel에서 AI랑 log 분석하면서 구글링하고 있었던 시간이 생각나서.

그리고 vercel에서 내 유행어 추천 서비스 **whatmeme** 도 호스팅하고있었는데 vercel 플랜이 오버돼서 이것도 AWS로 옮겨야 했다. 지금 생각해보면 여러 경험 하게되어서 좋았던거 같은데 저때는 조금 귀찮기도 했다.
